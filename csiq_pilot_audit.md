# CSIQ V5 Signal Android Pilot Audit

Generated by `csiq_pilot_audit.py`. No regression or predictive model was estimated.

Research question under exploration (not tested here):

> Does modeling interactions/configurations among software smells provide information beyond modeling individual software smells independently?

This audit only prepares data decisions. A later negative result on incremental value remains fully possible and is not treated as a failure of the dataset.

## A. Dataset structure

- Dataset root: `Dataset`
- Top-level tables: `repositories.csv`, `versions.csv`, `codesmells.csv`, `attribute-details.csv`, `synthesized/class_level_quality_code_smell_mdi.csv`.
- Per-project, per-version folders: `quality_attributes/<project>/<YYYY-1>.csv` and `codesmells/csv/<project>/<YYYY-1>.csv`.
- Smell HTML reports exist under `codesmells/html/<project>/design.html` (one file per project, not per version).
- GitHub issue dumps exist under `issues/` and are ticket-level, not class-level.
- `codesmells/Command.txt` shows PMD invoked as `pmd.bat -d <repo> -R category/java/design.xml -f csv`.
- Command file points at Signal Android and uses design.xml: `True`, `True`.
- `codesmells.csv` contains **47 rules** (catalog event totals, not unique classes).
- Quality files mix several row kinds in one CSV: a project/commit header, `<Package>` rows, `<Method>` rows, `<Field>` rows, `<Anonymous>` rows, inner/nested types, and top-level classes. Method and field rows are not class-level observations.
- Smell files are PMD violation-level records with fields `Problem, Package, File, Priority, Line, Description, Rule set, Rule`.
- `attribute-details.csv` documents quality metrics (WMC, CBO, LCOM, …), not PMD smells.
- `versions.csv` reports `Number of problematic classes` / `highly problematic classes`. For Signal Android those counts are 1–3 per year. That is a metric-based 'problematic class' flag (high coupling/complexity/low cohesion), **not** a PMD smell universe.

### Filtering / interpretation decisions

1. Class-level quality observations = unique `QualifiedName` values that are not `<Package>`, `<Method>`, `<Field>`, `<Anonymous>`, or other `<...>` structural rows. Project header rows without a dot are counted but are not usable WMC units.
2. Smell class key = `Package + '.' + basename(File without extension)`. Validated from the raw files, not taken on faith from prior notes.
3. Exact match = smell key equals quality `QualifiedName`. No fuzzy matching, no inner-class projection onto the enclosing type, no package-only match.
4. Inner/nested quality types are retained in counts but are reported separately because they almost never join to file-stem smell keys.
5. Absence from a smell CSV is **not** recoded as 'no smell'.
6. All 47 catalog rules are retained in the classification table. None were dropped for being inconveniently rare, noisy, or collinear; exclusion from the *pilot construct list* is a separate, documented decision.

## D. Signal Android smell/quality matching methodology

Join (validated from raw files):

```
smell_key = Package + '.' + basename(File)  # extension stripped
match if smell_key == quality.QualifiedName
```

This is a file-stem key. It can match a top-level type named like its `.java` file. It does not identify:

- inner/nested types (`Outer.Inner` in quality vs `pkg.Outer` from `Outer.java`)
- anonymous classes
- classes whose filename stem differs from the type name
- non-Java files (PMD was run with Java `design.xml`)

Two different coverage percentages are reported and must not be mixed:

1. **Smell-file → quality join rate**: `exact matches / unique classes in the smell file`. This answers: of PMD-violating file keys, how many land on a quality class?
2. **Quality-class smell-status coverage**: `exact matches / unique class-level quality observations`. This answers: for what fraction of quality classes do we observe at least one PMD violation record? It is **not** the fraction with known presence *or* absence.

If absence were (incorrectly) treated as zero, (2) would be 100% by definition. The files do not justify that.

PMD CSV structure evidence that the export is violation-only:

- Every smell row has a `Rule`. There are no clean-class placeholder rows.
- The `Problem` column restarts (it is not a global 1..N index of analyzed classes). In Signal 2016-1 there are 4357 violation rows but only 142 distinct Problem values.
- HTML reports are titled 'Problems found'.
- `Command.txt` uses `-f csv`, which emits violations, not analyzed-but-clean files.

## F. Whether zero-smell classes can be identified reliably

**No. Not from the tables present in this dataset.**

Checked and insufficient:

1. Smell CSVs: violation-only. `smell_file_contains_zero_violation_classes = no` for every Signal version.
2. Smell HTML: problems-found lists, and not even per version.
3. `versions.csv`: problematic-class counts are metric-based and tiny; they are not PMD coverage.
4. `attribute-details.csv`: metric dictionary only.
5. Synthesized MDI/GodClass table: 190707 rows across 60 filename values. **Signal Android rows = 11378** (kinds: {'project_header_or_unqualified': 6, 'top_level': 5870, 'anonymous': 1530, 'inner_or_nested': 3972}). `GodClass` value counts for Signal: {'0': 9083, '1': 2295}. This table **can** label non-GodClass classes under the MDI formula (`GodClass=0`). It **cannot** identify classes with zero PMD design.xml violations. PMD `GodClass` and synthesized `GodClass` are different operationalizations (PMD matched class-versions with GodClass in Signal = 257; synthesized Signal `GodClass=1` is much larger).
6. Issues CSVs: GitHub tickets (`Issue Title`, `State`, `Labels`). No QualifiedName, no PMD rules.
7. Repositories.csv: project metadata only.

Therefore:

- A class present in the smell CSV has ≥1 design.xml violation (known positive for at least one rule).
- A quality class absent from the smell CSV may be clean, unscanned, non-Java, filename-mismatched, inner/anonymous, or outside PMD's actual walk. Those alternatives cannot be separated with the files on disk.
- Encoding `absent = 0` would manufacture most of the 'no smell' class universe and is not licensed by the file structure.

A later sensitivity analysis *may* assume that PMD walked every `.java` file in the repo (Command.txt is consistent with that intent) and that top-level types whose names equal file stems form the analyzed universe. That would still be an assumption, not a proof, and must be labeled as such.

## G. Recommended candidate smell constructs for the pilot

The dataset does **not** support using all 47 rules as independent smells. It also does not require forcing a count of 5–8 if prevalence is too thin. Based on definitions, overlap, WMC contamination, and Signal matched class-version frequencies, the appropriate first-pilot set is **six primary constructs**, plus **two optional/conditional** ones.

### Primary (conceptually distinct; usable beside a WMC outcome if prevalence is adequate)

| Construct | Rule(s) to encode | Signal matched class-versions | Why |
| --- | --- | ---: | --- |
| data_class | `DataClass` | 246 | Classic design smell, not a WMC threshold. |
| long_method | `ExcessiveMethodLength` | 85 | Long Method. Keep this one size-of-method indicator; drop NCSS duplicates. |
| long_parameter_list | `ExcessiveParameterList` | 117 | Long Parameter List. Drop UseObjectForClearerAPI as a second variable. |
| mutable_global_state | `MutableStaticState` | 51 | Global mutable state. Do not include ImmutableField. |
| coupling_lod | `LawOfDemeter` | 3400 | Coupling smell. Among matched Signal class-versions it is near-saturated as a binary flag (~86%). Prefer violation counts, or drop the binary indicator. |
| god_class | `GodClass` | 257 | Classic smell, but high WMC contamination. Include only as a labeled, contaminated construct or hold out of WMC models. |

LawOfDemeter binary saturation among matched Signal class-versions: 3400 / 3953 = 86.01%. A binary LoD indicator is therefore a near-constant among PMD-positive classes. If LoD is kept, encode violation counts, not presence.

### Optional / do not add as extra independent smells

- **TooManyMethods** or **ExcessiveClassLength**: same large-class family as GodClass. Add at most one, and only if GodClass is excluded.

- **Cyclomatic / NCSS / Cognitive / NPath family**: do not use with WMC as the outcome.
- **ImmutableField**: not a smell.
- Boolean micro-rules and exception-signature conventions: not pilot constructs.

This is 6 constructs, not 47 and not a forced 8. Expanding to 8 by splitting cyclomatic variants or NCSS grains would manufacture independent variables that are the same construct.

## H. Risks / limitations discovered

1. **Violation-only smell export.** Zeroes are not observed.
2. **Grain mismatch.** PMD events are file/line/rule; quality is class (and inner/anonymous). File-stem join under-identifies inner types.
3. **LawOfDemeter saturation.** Catalog-wide this one rule dominates event counts. Class-level binary LoD may still be common enough to be uninformative.
4. **WMC tautology** if complexity-threshold rules or GodClass are used as predictors of WMC.
5. **Misleading catalog aliases.** ExcessivePublicCount is not Fowler 'Class Data Should be Private'. CyclomaticComplexity is not by itself 'Complex Class' as a distinct smell.
6. **Test vs main.** Smell paths include androidTest/test/main. Quality classes do not carry a test flag. Mixing them silently is a validity threat.
7. **Java-only PMD.** design.xml will not score Kotlin. Quality metrics may still include non-Java types. Unmatched keys can reflect language mix rather than cleanliness.
8. **Synthesized GodClass ≠ PMD universe.** Signal is in the MDI table, but `GodClass=0` is not 'no PMD smells'. PMD GodClass and MDI GodClass disagree in scale.
9. **Panel attrition.** Class-version persistence is uneven because the project grew (see below). A balanced six-year panel will be much smaller than 2021 headcount.
10. **Measurement discontinuities.** WMC transitions are inspected below; a high share of ΔWMC = 0 is expected and is not by itself evidence of stability of the *tool*.
11. **Co-occurrence ≠ interaction.** Pair counts in this audit are not Model B.
12. **Selected-on-smells bias** if the panel is restricted to classes that appear in smell CSVs.

## I. Proposed pilot schema (only what the files support)

| Field | Status | Source | Notes |
| --- | --- | --- | --- |
| `project` | derivable | directory name (10 Signal-Android-master) | Constant for this pilot. |
| `version` | observed | quality_attributes and codesmells csv filenames (YYYY-1) | Six annual snapshots 2016-1..2021-1. |
| `class` | observed | quality QualifiedName | Use exact QualifiedName. Inner/nested types are separate rows and generally do not join to PMD file-level keys. |
| `class_kind` | derivable | QualifiedName shape | top_level vs inner_or_nested vs project_header_or_unqualified. Anonymous/package rows should be excluded. |

| `WMC_t1` | observed | first WMC column in quality CSV at version t+1 | Only for classes with exact QualifiedName in both versions. |
| `delta_WMC` | derivable | WMC_t1 - WMC_t | Defined only for valid numeric transitions. Do not call this software corrosion. |
| `LOC_t` | observed | quality LOC | Candidate control; collinear with size smells. |
| `CBO_t` | observed | quality CBO | Candidate control; collinear with CouplingBetweenObjects / ExcessiveImports. |

## J. Explicit recommendations for the NEXT step

Next step is **dataset building**, still not modeling:

1. Build a Signal Android class-version panel of top-level types with numeric WMC.
2. Attach PMD construct counts for the six primary constructs via the validated join key.
3. Store `smell_status_known` = class appeared in that version's smell CSV. Do **not** recode the complement as zero in the canonical file.
4. Produce two analysis views later, without discarding the canonical file: (i) known-positive-only; (ii) optional sensitivity file where top-level java-like keys missing from PMD are set to zero **with an assumption flag**.
5. Compute consecutive-version `WMC_t`, `WMC_t1`, `delta_WMC` on exact QualifiedName.

## K. Answers to the six decision questions

1. **Is Signal Android suitable for the first pilot?** Conditionally yes for a *descriptive / panel-construction* pilot: six paired versions, high smell→quality join rate relative to other CSIQ projects, and usable WMC transitions. It is not yet suitable for a causal interaction model, and it is not suitable for treating missing smell rows as zeros.
2. **Which smell constructs should be tested?** DataClass, Long Method (`ExcessiveMethodLength`), Long Parameter List (`ExcessiveParameterList`), MutableStaticState, LawOfDemeter (if not saturated), and GodClass only with a WMC-contamination label. Not all 47 rules.
3. **Can we reliably define smell presence/absence?** Presence of a violation: yes, for keys in the smell CSV. Absence: **no**, not reliably. Presence/absence as a complete binary universe is not supported.
4. **Is WMC a viable first longitudinal outcome?** Yes as a numeric class-level outcome with lagged `WMC_t`, subject to attrition, inner-class noise, and the prohibition on using cyclomatic/GodClass-style predictors without a contamination discussion. ΔWMC = 0 is common; that is an outcome distribution fact, not a model result.
5. **Biggest methodological threat?** Encoding unknown smell status as 'no smell', compounded by using complexity-threshold PMD rules (or GodClass) to explain WMC, and interpreting co-occurrence as interaction.
6. **Exact next dataset-building step?** Write a Signal top-level class-version panel with observed WMC and observed PMD construct counts, plus a `smell_status_known` flag, without fabricating zeros and without running Model A/B.

## Methodological distinctions preserved

- Smell co-occurrence is not an interaction effect.
- Correlation is not causation.
- Multiple smell variables are not evidence of interaction.
- ML feature interaction is not necessarily a meaningful smell interaction.
- Smell prioritization is not configuration prioritization.
- The thesis is not trying to prove that smell interactions matter; it asks whether configuration information adds incremental value. A negative result is a valid scientific outcome.
